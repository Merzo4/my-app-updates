# 07 — CHANGE AND DECISION POLICY

## Что считается binding decision
Изменение архитектуры, UX-концепции, продуктовых профилей и их допустимого риска, защиты Windows, rollback, источника обновлений, схемы веток/SOT, релизного процесса и удаления данных. Обычный минимальный fix в рамках принятого контракта — defect checkpoint, если scope не расширяется.

## Процесс
1. Описать проблему и GitHub evidence.
2. Классифицировать Proposal / Defect / Security / Breaking Contract.
3. Указать affected files/modules, старое поведение, новое поведение, обратную совместимость, влияние на GAME/EXTREME/Undo/OTA.
4. Если новый выбор принципиален — получить owner decision до изменения.
5. Создать новый DECISIONS/YYYY-MM-DD-NNN-title.md. Старые решения append-only; отмена/изменение — новая запись с supersedes.
6. Выполнить тесты по risk boundary и записать REPORT + checkpoint + live state.

## Строгость релизов
Новая внешняя стабильная версия, destructive действие на пользовательской машине, удаление/миграция пользовательских данных и снятие защит не разрешаются «по умолчанию» даже после успешной компиляции. Нужна явная воля владельца и evidence.
